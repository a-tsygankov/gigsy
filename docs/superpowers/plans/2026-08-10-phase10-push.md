# Phase 10: Push Notifications Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reminders for the work a calendar can never surface — a lead that
goes stale and an invoice that goes unpaid. Both are undated by nature, which
is precisely the gap the Phase 7 "no push in v1" decision left open
(docs/plan.md §13, §14).

**Decisions (pinning the open items):**

### 1. Encrypted payloads, not a content-free "tickle"

The cheap route is a payload-less push that wakes the service worker and lets
it fetch what to say. **Rejected**: the worker would need to authenticate, which
means reading the rotating, single-use refresh token out of IndexedDB in a
second context and racing the page for it. That is exactly the bug fixed a few
hours ago in `AuthManager.refreshOnce()` — and a shared in-flight promise cannot
span a page and a service worker, so the fix would not even apply.

So the worker sends an **encrypted payload (RFC 8291, `aes128gcm`)** and the
service worker needs no credentials at all. The crypto is unpleasant but
completely specified and testable offline against the RFC's own vectors, which
is a far better risk than a token race that only shows up in production.

### 2. VAPID keys

- `VAPID_PUBLIC_KEY` is a **var** — it is public by definition; the browser
  needs it to subscribe.
- `VAPID_PRIVATE_KEY` is a **secret** (`wrangler secret put`), added to
  `scripts/setup-secrets.ps1` with the same GENERATE treatment as the other
  keys. Rotating it invalidates every existing subscription — the same
  foot-gun that broke the calendar connection, so subscriptions are pruned on
  the first rejection rather than left to fail forever.
- Signing is ES256 over P-256, which WebCrypto does natively.

### 3. What earns a notification

Only things a calendar cannot tell you:

- a **lead** untouched for 7 days — it will never appear on a calendar, because
  leads deliberately never sync;
- a **completed** gig still unpaid after 14 days.

Confirmed, dated work is left alone: it is already on the calendar with a
reminder (Phase 9.1), and duplicating that is how notification fatigue starts.

**At most one notification per user per day**, carrying the single most
pressing item. A per-user `last_push_at` plus the nudge's identity key means a
run that finds nothing new stays silent instead of re-sending every 15 minutes.

### 4. Subscriptions

- `push_subscriptions` (migration 0007): endpoint (PK — the push service's own
  identifier), user, `p256dh`, `auth`, `created_at`.
- A `404`/`410` from the push service means the subscription is dead:
  **delete the row**, don't retry. Same lesson as the calendar — a credential
  that can rot needs a pruning path or the failure becomes permanent and silent.
- Multiple devices per user are supported by construction; each subscription is
  its own row.

### 5. iOS reality, stated up front

Safari only delivers Web Push to a PWA **installed to the home screen**, and
permission must be requested from a real user gesture. The UI therefore asks
only on an explicit tap, and says plainly what to do when
`Notification.permission` is unavailable — rather than appearing broken on the
platform this app primarily targets.

### 6. Service worker

The app currently uses vite-plugin-pwa's `generateSW`, which cannot host custom
code. This moves to **`injectManifest`**, where precaching becomes an explicit
`precacheAndRoute(self.__WB_MANIFEST)` next to the `push` and
`notificationclick` handlers. Risk noted: precaching is now our code rather than
generated, so the offline-reopen behaviour must be re-verified.
